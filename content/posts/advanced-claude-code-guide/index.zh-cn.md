用 Claude Code 也有一段时间了，从最开始的简单对话修改代码，到现在逐渐能处理一些复杂的任务。最近专门花时间学习了一些在之前的使用过程中忽略的的“进阶技巧”，发现还是有不少功能用得不够深入。

这篇文章不是完整的教程，更像是我个人的学习笔记——记录那些让我觉得“早点知道就好了”的功能和经验。主要关注三个方向：处理复杂任务的方法、性能和上下文的精细控制、以及如何通过扩展生态突破默认能力边界。

如果你也在用 Claude Code，但感觉还没完全发挥出它的潜力，希望这些笔记能给你一些启发。

## 复杂任务的正确打开方式

一开始用 Claude Code 时，我基本都是“想到什么就直接让它做”。简单任务没问题，但遇到复杂的多步骤任务时，经常会遇到做到一半发现方向不对，或者改了一堆文件最后发现有更好的方案。后来逐渐发现，处理复杂任务需要一些“前置步骤”和“安全机制”。

### Plan模式：先规划再动手

#### 什么是 Plan 模式

Claude Code 默认的工作方式是”直接执行”：你提出需求，它立刻开始动手改代码。这种方式对简单任务很高效，但处理复杂任务时容易出问题——方案选择、文件依赖、潜在风险都没有提前梳理，做到一半才发现方向不对。

Plan 模式是一种”两阶段工作流”：
1. **规划阶段**：Claude 先探索代码库、设计方案、列出步骤，将计划写入专门的 plan 文件
2. **执行阶段**：你确认 plan 后，Claude 再按计划实施

这样做的好处是把”思考”和”动手”分开，让你能在改代码前就发现问题。

#### 如何进入 Plan 模式

有两种方式：
1. **Claude 主动询问**：当它判断任务足够复杂时，会弹出提示询问是否进入 plan 模式
2. **你主动要求**：在提任务时明确说明，比如：
   - “先制定一个实现计划”
   - “用 plan 模式处理这个需求”
   - “不要直接动手，先给我一个方案”
   - 或者直接使用 `/plan` 命令

如果你希望 Claude 对某类任务始终先 plan，可以在项目的 `CLAUDE.md` 文件里写明。

#### 为什么需要 Plan 模式

最初我不太理解它的价值，直到有一次我想给一个数据分析项目添加导出功能，需求是”支持导出 CSV 和 Excel 两种格式”。我直接让 Claude 开始做，它的实现路径是：

1. 在 API 层添加 `/export` 端点
2. 在服务层写导出逻辑，用 `pandas.to_csv()` 和 `pandas.to_excel()`
3. 前端添加导出按钮

看起来挺合理，但做到一半我突然意识到：项目里的数据集有些很大（几十万行），直接在内存里转换可能会 OOM。而且已有的数据查询逻辑分散在好几个地方，导出时需要重新组装，但 Claude 用的简化逻辑和实际查询不一致。

这时候已经改了 4 个文件，回退很麻烦。

后来我用 Plan 模式重新做了一遍这个需求。Claude 先花了几分钟探索代码，然后给出的 Plan 里指出：
- 现有查询逻辑在 `QueryBuilder` 类里，导出应该复用而不是重写
- 大数据集需要流式导出，建议用 `StreamingResponse`
- Excel 导出依赖 `openpyxl`，需要先检查是否已安装
- 方案对比：同步导出 vs 异步任务队列（最终选了同步+流式，因为项目没有任务队列基础设施）

这个 Plan 让我在动手前就发现了潜在问题，最终实现很顺利。

#### 什么时候值得用 Plan 模式

不是所有任务都需要 plan，关键是判断”提前规划的收益”是否大于”多一个步骤的成本”。我总结了一个对比表：

| 任务特征 | 建议用 Plan 模式 | 可以跳过 Plan，直接做 |
|---------|----------------|---------------------|
| **文件数量** | 需要修改 3+ 个文件，且文件间有依赖关系 | 单文件修改，或多文件但改动独立 |
| **架构决策** | 需要选择设计模式、技术方案、放在哪一层 | 实现方式明确，没有分叉选择 |
| **不确定性** | 需求模糊，有多种实现路径 | 需求清晰，实现路径唯一 |
| **风险程度** | 大数据处理、权限控制、数据库迁移等高风险操作 | 低风险改动，如 UI 调整、文案修改 |
| **回退成本** | 做错了很难回退（已改多个文件、涉及数据变更） | 容易回退（改动局部、无副作用） |

**典型场景举例：**

**应该用 Plan：**
- “给项目添加用户认证系统”（涉及多层架构、安全考虑）
- “重构数据库查询模块以支持分页”（性能敏感、影响多处调用）
- “实现导出功能支持 CSV/Excel”（方案选择、大数据处理）

**可以跳过 Plan：**
- “把按钮文字从'提交'改成'确认'”（单一改动）
- “在配置文件里添加一个新的环境变量”（明确操作）
- “修复拼写错误”（局部修改、零风险）

简单说：**如果任务”做错了成本很高”或者”有多条路可走”，就值得先 plan。**

#### 好的 Plan 应该包含什么

一开始我以为 Plan 就是列 TODO list，后来发现内容深度差很多。好的 Plan 应该包含：

- **方案对比**：如果有多种实现路径，说明为什么选 A 不选 B（技术约束？成本考虑？风险评估？）
- **风险点**：哪些地方可能出问题？需要特别注意什么？（性能瓶颈、兼容性、边界情况）
- **文件清单**：具体要改哪些文件，每个文件的改动性质（新增/修改/删除）
- **依赖检查**：需要安装新的库吗？需要修改配置吗？

举个例子，之前让 Claude 给项目添加缓存层，它给出的 Plan 里不仅列出了要改的文件，还说明了为什么选 Redis 而不是本地内存缓存（因为项目后续可能多实例部署），以及缓存失效策略的考虑（TTL + 主动失效）。这种 Plan 让我能在执行前判断方向对不对，而不是等实现完了再发现问题。

### Subagents：委派与并行

#### 什么是 Subagents

Subagent 是 Claude Code 中的“任务委派”机制。当你在主对话中请求 Claude 处理任务时，它可以创建一个或多个独立的“子会话”（subagent），每个 subagent 拥有完整的工具能力，可以读文件、搜索代码、执行命令，完成后将结果返回给主对话。

Subagent 的关键特性：
- **独立上下文**：看不到主对话的历史，避免主对话被大量中间结果污染
- **并行执行**：多个 subagent 可以同时工作，互不干扰
- **结果汇总**：subagent 只返回最终结论，冗长的探索过程不会进入主对话

#### 如何使用 Subagents

有两种方式触发：
1. **Claude 自主判断**：当它发现某个子任务适合独立处理时，会自动 spawn subagent
2. **你明确要求**：在提任务时指明，比如：
   - "请 spawn 一个 subagent 去搜索所有调用 X 函数的地方"
   - "用 subagent 并行跑测试和检查文档"

注意：你不能直接"进入" subagent 对话，它是由主对话中的 Claude 创建和管理的。

#### 为什么需要 Subagents

起初我不太理解它的价值——“既然我能直接问 Claude，为什么要让它再去问另一个 Claude？”直到有一次我让 Claude 帮我分析一个大型项目的依赖关系。

主对话里很快就塞满了搜索结果、文件列表、依赖树，我想讨论“发现了哪些问题”时，得往上翻很久才能找到之前的讨论。更糟的是，这些中间结果占用了大量上下文，导致后续对话的成本很高。

后来我学会了主动要求用 subagent：让它 spawn 一个 subagent 专门做“依赖分析”，主对话里只收到最终的总结报告（“发现 3 个循环依赖，5 个未使用的依赖”），过程细节都在 subagent 里，主对话保持干净。

**典型使用场景：**

| 场景 | 为什么适合用 Subagent |
|------|---------------------|
| **大范围代码搜索** | 搜索结果可能有几十上百条，塞满主对话；subagent 筛选后只返回关键发现 |
| **并行的独立任务** | 比如同时跑测试 + 检查文档一致性，两者互不依赖，并行更快 |
| **探索性研究** | 比如"调研项目用了哪些第三方库"，研究过程冗长但你只需要结论 |
| **危险实验** | 配合 `isolation: "worktree"`，让 subagent 在隔离环境里做高风险改动 |

#### 用好 Subagents 的关键

**1. 写好 Prompt 很重要**

给 subagent 的 prompt 不同于直接对话，因为它**看不到主对话历史**。我学到的经验：

- **上下文要自给自足**：不要说“帮我看看这个问题”（它不知道“这个问题”是什么），而是"在 `src/` 目录下搜索所有调用 `legacyAuth()` 函数的地方，列出文件路径和行号"
- **明确交付物格式**：要列表？要统计数字？要代码示例？说清楚
- **控制操作范围**：如果只需要分析，明确说"只读，不要修改文件"；如果可以改代码，说明改动的边界

**2. 并行 vs 串行的判断**

并不是"能并行就并行"，要看任务依赖关系和整合成本：

| 判断维度 | 适合并行 | 适合串行 |
|---------|---------|---------|
| **任务依赖** | 任务 A 和 B 完全独立，互不依赖 | 任务 B 需要用到任务 A 的结果 |
| **结果整合** | 结果可以直接并列展示，无需交叉分析 | 结果需要联合分析才有意义 |
| **执行时间** | 两个任务都比较耗时，并行能明显节省时间 | 任务很快，并行的协调成本反而更高 |

有一次我让两个 subagent 分别分析前端和后端的性能问题，结果发现很多瓶颈其实是前后端交互导致的（API 调用频次、数据传输量），分开分析后我得自己整合，反而增加了工作量。这种情况下，串行或者直接在主对话里做更合适。

**3. 什么时候不该用 Subagent**

- **任务很简单**：读一个文件、改几行代码，直接做比委派更快
- **需要频繁交互**：如果你预期会多轮追问，subagent 不适合（它是一次性任务）
- **上下文高度相关**：如果任务严重依赖主对话的历史上下文，拆出去反而要花很多字解释背景

### Git Worktrees：安全的沙盒实验

#### 什么是 Git Worktrees

Git Worktrees 是 Git 的一个功能，允许你在同一个仓库下同时维护多个工作目录，每个目录可以在不同的分支上工作。在 Claude Code 中，这个功能被包装得更易用，让你能快速创建一个“平行空间”来做实验性改动。

关键特性：
- **隔离环境**：每个 worktree 有独立的工作目录和分支，互不干扰
- **共享仓库**：底层共享同一个 `.git` 目录，不会重复克隆整个项目
- **随时切换**：可以在主分支和 worktree 之间自由切换，无需 stash 或 commit

#### 如何使用 Git Worktrees

在 Claude Code 中使用 worktree 很简单：

```bash
/worktree <worktree-name>
```

比如 `/worktree refactor-auth` 会创建一个新的 worktree 并自动切换进去。

退出 worktree 并清理：
- 使用 `exit worktree` 命令
- 选择 `keep`（保留代码，后续可以合并）或 `remove`（删除整个 worktree）

#### 为什么需要 Git Worktrees

之前我都是直接在分支上让 Claude 改代码，有几次遇到这种情况：
- 让 Claude 尝试一个“激进”的重构方案，改到一半觉得不行，想回退但已经改了十几个文件，`git reset` 很麻烦
- 正在处理一个功能，突然来了个紧急 bug 需要修，但当前改动还没到可以提交的状态，得 stash、切分支、修完再切回来
- 想对比两种实现方案的实际效果，但不想来回切分支、重新跑构建

后来发现 Git Worktrees 完美解决这些问题——它相当于给你一个“平行空间”，可以放心实验，失败了直接删掉，主分支完全不受影响。

| 场景 | 如何使用 Worktree | 收益 |
|------|-----------------|------|
| **危险重构** | 在 worktree 中尝试大规模重构 | 失败了直接 remove，成功了再合并回主分支，零风险 |
| **A/B 方案对比** | 创建两个 worktree，分别实现不同方案 | 可以运行、测试、对比真实效果，而不是纸上谈兵 |
| **临时切换任务** | 在 worktree 里继续开发 feature，主分支处理紧急 bug | 无需 stash，两个任务的上下文完全隔离 |
| **配合 Subagent 做实验** | `isolation: "worktree"` 让 subagent 在隔离环境工作 | 高风险操作不会污染主分支，实验完成自动清理 |


#### 使用建议

**1. 明确实验目的**

进入 worktree 前想清楚：
- 我要验证什么？（性能提升？代码可维护性？新方案可行性？）
- 成功的标准是什么？（测试通过？性能指标达标？）
- 失败了怎么办？（直接放弃？还是调整方案？）

避免在 worktree 里漫无目的地改来改去，最后连自己都不知道改了什么。

**2. 及时清理**

实验结束后立即决定：
- **Keep**：验证成功的方案，准备合并回主分支
- **Remove**：失败的尝试、临时测试、已经合并的改动

不要堆积一堆废弃的 worktree，既占磁盘空间，也容易混淆。

**3. 利用 isolation 特性**

当你让 Claude 使用 subagent 做高风险操作时，可以明确要求：
> "用 subagent 在 worktree 里尝试重构认证模块，如果测试通过就保留，否则丢弃"

这样 subagent 的实验性改动被隔离在 worktree 中，不会影响你的主工作环境。

## 上下文与性能的精细控制

使用 Claude Code 一段时间后，我开始注意到上下文管理和性能调优的重要性。有时候对话变得“迟钝”，有时候 Claude 的回答质量突然下降，这些问题往往和上下文污染或 effort 级别设置不当有关。

### 会话管理：保持对话的清晰度

会话管理指的是如何维护、清理和延续你与 Claude 的对话上下文。每次对话都会累积历史消息，这些消息既是 Claude 理解你需求的基础，也可能成为干扰和成本的来源：

- **上下文窗口**：Claude 能“记住”的对话历史长度（虽然很大，但不是无限的）
- **上下文污染**：历史对话中的错误信息、过时假设、无关细节干扰当前任务
- **上下文成本**：更长的历史意味着更高的 token 消耗和响应延迟

**核心命令**：
- `/clear`：清空当前会话，开始全新对话
- `/continue`：在新会话中延续上一次对话的上下文（跨会话记忆）

#### 什么时候该 /clear

一开始我几乎不用 `/clear`，觉得“历史越多，Claude 越了解我的项目”。但后来发现有些情况下，历史反而成了负担。

我现在的判断标准：

| 场景 | 说明 | 是否该 clear |
|------|------|-------------|
| **重复犯错** | Claude 多次给出同样的错误方案，即使你已经纠正过 | ✅ 上下文里可能有误导性信息 |
| **偏离主题** | 对话从 A 任务跳到 B 任务又跳到 C 任务，历史变得混乱 | ✅ 新任务重新开始更清晰 |
| **响应变慢** | Claude 的回复明显变慢，或开始”思考”很久 | ✅ 上下文太长影响性能 |
| **任务完全切换** | 从前端开发切换到数据库优化，两者完全无关 | ✅ 旧上下文没有价值 |
| **方案已推翻** | 之前讨论的方案已经放弃，但历史里全是那些讨论 | ✅ 避免 Claude 参考错误方案 |
| **同一项目深度工作** | 持续在同一模块上迭代，历史对话都是有价值的上下文 | ❌ 保持历史有助于理解 |
| **需要项目全局视角** | 需要 Claude 记住之前讨论的架构决策和约定 | ❌ 清空会丢失项目知识 |

**对于不应该 clear 的场景，如何应对上下文问题：**

当你需要保持项目知识但又担心上下文过长时，更好的做法是：
- **使用 CLAUDE.md**：将重要的架构决策、项目约定写入 `CLAUDE.md` 文件（详见第三部分），这样即使 clear 了，Claude 也能通过读取文件获取项目知识
- **使用 Memory**：Claude Code 有持久化记忆功能，可以将反复提及的项目信息、用户偏好存入 Memory，跨会话保留
- **主动总结**：在 clear 前，让 Claude 总结当前的关键决策和进展，clear 后把总结粘贴回来作为新对话的开头


#### 什么时候用 /continue

`/continue` 的价值在于**跨会话延续**。当你关闭了 Claude Code 或切换了工作目录，但后续还想继续之前的讨论时，用 `/continue` 可以让 Claude "记起"上一次的上下文。

典型场景：
- **跨天继续工作**：昨天讨论了重构方案，今天想继续实施
- **切换工作目录后回来**：临时去别的项目处理事情，回来后想接着之前的任务
- **意外中断后恢复**：Claude Code 崩溃或网络断开，重启后想恢复进度

注意：`/continue` 不是万能的，它依赖于之前会话的记录。如果你主动 `/clear` 了，就无法 continue 回去。

#### 上下文 vs Memory

容易混淆的是：会话上下文和 Memory 有什么区别？

**Memory 是什么：**

Memory 是 Claude Code 的持久化记忆系统，以文件形式存储在项目目录下（通常在 `.claude/projects/<project-name>/memory/`）。当你明确告诉 Claude"记住这个"，或者某些信息反复出现时，Claude 会将其写入 Memory 文件，后续会话中可以读取。

**上下文 vs Memory 的区别：**

| 维度 | 会话上下文 | Memory |
|------|-----------|--------|
| **生命周期** | 当前对话或相邻的几次对话 | 长期存储，跨多次会话 |
| **内容性质** | 具体的任务讨论、中间结果、临时决策 | 项目知识、用户偏好、反复验证的经验 |
| **何时清理** | 任务切换、上下文污染、性能下降时 | 信息过时或错误时 |
| **查询成本** | 免费（已在对话中） | 需要显式读取 Memory 文件 |
| **存储位置** | 在内存中，关闭会话后通过 `/continue` 恢复 | 文件系统中，永久保存 |

简单说：**上下文是短期记忆，Memory 是长期记忆。**

**何时使用 Memory：**
- 项目的架构约定（"我们统一用 Repository 模式访问数据库"）
- 用户偏好（"测试文件统一放在 `__tests__` 目录"）
- 反复踩过的坑（"这个 API 有 rate limit，需要加重试逻辑"）

这样即使 `/clear` 了会话，重要的项目知识仍然保留在 Memory 中。

### Effort 级别：在速度和深度之间找平衡

Effort 级别控制 Claude 在回答问题时的”思考深度”。Claude Code 支持四个级别：
- **low**：快速响应，适合简单任务
- **medium**：平衡速度和质量
- **high**：深度思考（默认）
- **max**：最深度的思考和推理，适合最复杂的问题

可以通过 `/effort <level>` 切换，或在提问时临时指定。

#### 四个Effort级别的差异

一开始我以为 effort 只是影响速度，后来发现差异不止于此：

| 维度 | Low | Medium | High（默认） | Max |
|------|-----|--------|------------|-----|
| **响应速度** | 很快 | 适中 | 较慢 | 最慢 |
| **思考深度** | 浅层分析 | 常规推理 | 深度推理、多角度权衡 | 最深度推理、穷尽可能性 |
| **适用任务** | 简单修改、查询、格式化 | 中等复杂度的开发任务 | 架构设计、复杂重构、难题调试 | 极端复杂的问题、关键决策 |
| **成本** | 低 | 中 | 高 | 最高 |
| **容易出错** | 简单任务不会，复杂任务容易 | 平衡 | 复杂任务也能处理好 | 极少出错 |

#### 如何选择 Effort 级别

我的经验是按**任务性质**而非任务大小来选择：

**Low effort 适合：**
- 代码格式化、重命名变量
- 简单查询（”这个函数在哪里定义的？”）
- 写测试用例（逻辑已明确，只是写代码）
- 文档生成、注释添加

**Medium effort 适合：**
- 日常开发任务（不太复杂的功能实现）
- Bug 修复（问题已定位）
- 代码审查（常规检查）
- 简单重构

**High effort 适合（默认，大部分场景）：**
- 架构决策（”应该用微服务还是单体？”）
- 复杂重构（跨多个模块，影响广泛）
- 难题调试（问题原因不明确）
- 性能优化（需要权衡多种方案）
- Plan 模式（规划本身就需要深度思考）

**Max effort 适合：**
- 关键架构决策（影响长期技术栈选择）
- 极其复杂的 bug（涉及多个系统交互、难以复现）
- 安全漏洞分析（需要考虑各种攻击向量）
- 生产事故分析（需要穷尽所有可能原因）

#### 成本意识

High 和 max effort 的成本更高（时间和 token），需要根据场景权衡。我的策略是：
- **探索阶段**（不确定方向）：用 high 甚至 max effort，花时间思考值得
- **执行阶段**（方案已定）：降到 medium 或 low，快速实施
- **迭代优化**（小调整）：用 low，保持开发流畅
- **关键决策**（影响深远）：不吝惜用 max effort，避免方向性错误

有时候我会在同一个任务中动态调整：先用 high/max effort 确定方案，再切换到 medium/low 执行具体的代码修改。

由于默认就是 high effort，对于大部分任务我不需要手动调整。只在“确实很简单”的任务时降到 low/medium，或“极端复杂”的问题时升到 max。

## 项目知识的持久化与复用——CLAUDE.md

前面提到了会话管理和 Memory，但还有一个更重要的持久化机制：**CLAUDE.md**。如果说 Memory 是“个人笔记”，那 CLAUDE.md 就是“项目文档”——它是整个团队共享的项目知识库。

#### 什么是 CLAUDE.md

CLAUDE.md 是一个放在项目根目录的 Markdown 文件，Claude Code 会在每次对话开始时自动读取它。你可以在里面写任何希望 Claude“永远记住”的项目信息：架构决策、开发约定、特殊的上下文、常见问题的解决方案等。

关键特点：
- **自动加载**：Claude 启动时自动读取，无需手动提醒
- **版本控制**：可以提交到 Git，团队成员共享同一份项目知识
- **优先级高**：比会话上下文和 Memory 更优先，Claude 会严格遵循其中的指示
- **持久有效**：不会因为 `/clear` 而丢失

#### 为什么需要 CLAUDE.md

有一次我在一个多人协作的项目中遇到问题：每次新同事用 Claude Code 时，都要重新解释一遍项目的特殊约定（"我们用 Repository 模式"、"测试文件统一放 `__tests__` 目录"、"API 错误码用四位数字"）。而且即使是我自己，过几天 `/clear` 后，也得重新说一遍。

后来我创建了 CLAUDE.md，把这些约定写进去。从此以后，无论是谁、无论什么时候用 Claude Code，它都能“记住”这些规则，新手和老手拿到的都是同样完整的项目上下文。

#### CLAUDE.md 应该写什么

**适合写进 CLAUDE.md 的内容：**

| 类型 | 具体内容 | 例子 |
|------|---------|------|
| **架构约定** | 项目的技术栈、设计模式、分层结构 | "使用 Clean Architecture，Domain 层不依赖任何外部框架" |
| **开发规范** | 代码风格、命名规则、文件组织 | "组件文件名用 PascalCase，hooks 文件名用 camelCase" |
| **特殊上下文** | 项目的独特背景、历史包袱、技术债 | "auth 模块正在从 JWT 迁移到 OAuth2，两套逻辑并存" |
| **常见陷阱** | 容易踩的坑、性能瓶颈、已知 bug | "ORM 的 eager loading 有 bug，必须手动 join" |
| **工作流指引** | 特定任务的处理流程、工具使用 | "添加新 API 时，记得同步更新 OpenAPI spec" |
| **外部依赖说明** | 关键第三方库的特殊用法、版本限制 | "Redis 客户端必须用 4.x，5.x 有兼容性问题" |

**不应该写进 CLAUDE.md 的内容：**

- **会快速过期的信息**：当前的 TODO、正在进行的任务、临时决策（这些应该在会话中或 plan 文件里）
- **过于具体的实现细节**：某个函数的具体实现（代码本身就是文档）
- **个人偏好**：某个开发者的习惯（应该在个人 Memory 里）
- **敏感信息**：密码、API key、内部URL（应该在配置文件或环境变量里）

#### 一个实际的 CLAUDE.md 示例

```markdown
# 项目上下文

## 技术栈
- **后端**: Python 3.11 + FastAPI + SQLAlchemy
- **数据库**: PostgreSQL 14
- **缓存**: Redis 6.x （注意：必须用 6.x，7.x 的 ACL 功能与我们的部署环境不兼容）
- **测试**: pytest + httpx

## 架构约定

### Repository 模式
所有数据库访问必须通过 Repository 层，不允许在 Service 或 Controller 里直接写 SQL。

### 错误处理
- API 错误码统一用四位数字（1xxx 客户端错误，2xxx 服务端错误）
- 所有异常必须在 Controller 层捕获并转换为标准错误响应

## 开发规范

### 文件组织
```
src/
├── domain/       # 领域模型和业务逻辑
├── repository/   # 数据访问层
├── service/      # 应用服务层
├── api/          # API 路由和控制器
└── tests/        # 测试文件（镜像 src 目录结构）
```

### 测试要求
- 所有 API 端点必须有集成测试
- Repository 层必须有单元测试（mock 数据库）
- 测试文件命名：`test_<模块名>.py`

## 特殊上下文

### 认证模块迁移中
auth 模块正在从 JWT 迁移到 OAuth2（2024-08 开始）。当前两套逻辑并存：
- `/api/v1/auth/*` 仍用 JWT（兼容老客户端）
- `/api/v2/auth/*` 已切换到 OAuth2
- 修改认证逻辑时，确认清楚是哪个版本

### 已知性能瓶颈
`/api/v1/users` 端点在用户量 >10k 时性能下降明显，原因是 N+1 查询。
临时方案：加了 Redis 缓存（TTL 5min）。
长期方案：重构为分页 + eager loading（已在 backlog）

3. 在 `repository/` 下添加数据访问方法（如需要）
4. 更新 `openapi.yaml`
5. 在 `tests/api/` 下添加集成测试

#### 如何维护 CLAUDE.md

**1. 随项目演进更新**

CLAUDE.md 不是一次性写完就不动的文档，它应该随着项目演进持续更新：
- 架构重构后，更新架构约定
- 发现新的常见陷阱，补充到文档
- 技术债还清了，删除相关说明

**2. 保持简洁有效**

不要把 CLAUDE.md 当成知识库堆砌所有东西。每条信息都问自己：
- Claude 需要这个信息才能正确工作吗？
- 如果没有这个信息，Claude 可能会犯错吗？
- 这个信息有更好的存放位置吗（比如代码注释、README、Wiki）？

只保留“高价值、高频使用”的信息。

**3. 团队协作**

如果是团队项目：
- 把 CLAUDE.md 纳入 code review 流程
- 当有新成员问“为什么要这么做”时，考虑是否应该写进 CLAUDE.md
- 定期回顾（比如每个 Sprint），删除过时内容

#### CLAUDE.md vs Memory vs 会话上下文

三者的定位和使用场景：

| 维度 | CLAUDE.md | Memory | 会话上下文 |
|------|-----------|--------|-----------|
| **作用范围** | 整个项目，所有人共享 | 单个用户在该项目的个人记忆 | 当前对话 |
| **生命周期** | 永久（除非手动删除） | 长期（跨会话） | 短期（当前会话） |
| **版本控制** | ✅ 提交到 Git | ❌ 本地文件 | ❌ 不持久化 |
| **典型内容** | 架构约定、开发规范、项目背景 | 个人偏好、个人踩过的坑 | 当前任务的讨论、临时决策 |
| **何时使用** | 所有人都需要知道的项目知识 | 个人的长期偏好和经验 | 当前任务的具体细节 |

**使用原则：**
- **团队共识** → CLAUDE.md
- **个人经验** → Memory  
- **临时讨论** → 会话上下文


## 扩展生态：突破默认能力边界

Claude Code 本身已经很强大，但通过扩展机制可以进一步突破能力边界。目前主要有四种扩展方式：**Skills**、**Hooks**、**MCP**、**Plugins**。

### 四种扩展方式的对比

我们先建立一个整体认知：

| 扩展方式 | 定位 | 学习成本 | 灵活性 | 典型场景 |
|---------|------|---------|-------|---------|
| **Skills** | 预制能力包，开箱即用 | 低（会用命令即可） | 低（按设计使用） | SEO 审计、安全审查、代码审查 |
| **Hooks** | 自动化触发器 | 中（需要写 shell 脚本） | 中（可自定义脚本） | Pre-commit 检查、文件保存后自动格式化 |
| **MCP** | 外部工具集成 | 中（需要配置服务器） | 高（可访问任何 API） | 连接数据库、调用第三方 API、读取外部数据 |
| **Plugins** | 功能增强模块 | 低到中 | 中到高 | 增强现有功能、添加新工具 |

### Skills：预制能力包

Skills 是 Claude Code 官方或社区提供的“预制能力包”，每个 skill 封装了一套完整的工作流。比如 `/seo` skill 可以做完整的 SEO 审计，`/review` skill 可以做代码审查。

使用方式很简单：
```
/skill-name [参数]
```
#### 何时使用 Skills

Skills 适合**标准化、重复性的任务**。判断标准：
- 这个任务有明确的流程和检查项吗？
- 这个任务需要反复做吗？
- 社区有现成的 skill 吗？

如果三个问题都是"是"，用 skill 比每次手动描述需求更高效。


### Hooks：工作流自动化

Hooks 是“事件触发器”——当特定事件发生时（比如文件保存、提交代码），自动执行你预设的脚本。类似 Git hooks，但作用范围更广。

常见 hook 类型：
- **pre-commit**: git commit 前执行
- **post-edit**: 文件编辑后执行
- **on-save**: 文件保存时执行

#### Hooks的使用场景

**场景 1：自动格式化代码**

我配置了一个 `post-edit` hook，每次 Claude 编辑 Python 文件后自动运行 `black`：

```json
{
  "hooks": {
    "post-edit": {
      "command": "black {file}",
      "filePattern": "*.py"
    }
  }
}
```

这样 Claude 改完代码，格式化自动完成，不用手动跑 formatter。

**场景 2：Pre-commit 检查**

在 commit 前自动运行 linter 和测试：

```json
{
  "hooks": {
    "pre-commit": {
      "command": "npm run lint && npm test"
    }
  }
}
```

如果检查失败，commit 会被阻止，避免提交有问题的代码。

#### Hooks vs 手动执行

| 维度 | Hooks | 手动执行 |
|------|-------|---------|
| **触发方式** | 自动（事件驱动） | 需要记得手动运行 |
| **一致性** | 每次都会执行，不会遗漏 | 容易忘记或跳过 |
| **适用场景** | 重复性、规则性的检查 | 偶尔需要的操作 |
| **配置成本** | 需要配置 hook | 无需配置 |

**使用建议：**
- 把"容易忘但很重要"的检查配成 hook（格式化、linting、测试）
- 不要过度使用 hook，否则每次操作都要等一堆脚本跑完


### MCP：外部工具集成

MCP (Model Context Protocol) 是 Claude Code 连接外部工具和数据源的标准协议。通过 MCP，Claude 可以：
- 查询数据库
- 调用第三方 API（GitHub、Jira、Notion 等）
- 读取外部文件系统
- 执行复杂的系统操作

#### MCP的使用场景

**场景 1：数据库查询**

安装 MCP 数据库服务器后，Claude 可以直接查询数据库：
> "查一下 users 表里最近注册的 10 个用户"

Claude 会通过 MCP 连接数据库，执行 SQL，返回结果。

**场景 2：第三方 API 集成**

比如 GitHub MCP，Claude 可以：
- "列出这个仓库的 open issues"
- "创建一个 PR"
- "检查 CI 状态"

**场景 3：DataForSEO（SEO 数据）**

如果安装了 DataForSEO MCP，Claude 可以获取实时 SEO 数据：
- 关键词搜索量和难度
- SERP 分析
- 竞品排名

#### MCP vs 其他扩展方式

MCP 的独特价值在于**打通外部数据源**。Skills 和 Hooks 只能操作本地项目，MCP 让 Claude 能“看到”项目外的世界。

**何时使用 MCP：**
- 需要访问外部 API 或数据库
- 需要实时数据（不是本地文件里的静态信息）
- 需要跨系统协作（代码库 + issue tracker + CI/CD）


### Plugins：功能增强

Plugins 是扩展 Claude Code 核心功能的模块。与 Skills 不同，Plugins 更偏向“增强工具能力”而非“提供工作流”。

**常见 Plugin 类型：**
- 编辑器集成（VS Code、JetBrains 等）
- 新的文件格式支持
- 自定义工具和命令

容易混淆的是 Plugins 和 Skills 的区别：

| 维度 | Skills | Plugins |
|------|--------|---------|
| **定位** | 预制工作流（做完整的任务） | 功能增强（扩展工具能力） |
| **调用方式** | `/skill-name` 命令 | 后台运行或通过配置启用 |
| **例子** | `/review`（代码审查流程） | VS Code 插件（编辑器集成） |


### 如何选择扩展方式？

当你想扩展 Claude Code 的能力时，按这个决策树选择：

```
需要扩展能力
├─ 是标准化任务？
│  ├─ 是 → 先找 Skills
│  └─ 否 → 继续
├─ 需要自动化执行？
│  ├─ 是 → 用 Hooks
│  └─ 否 → 继续
├─ 需要外部数据/API？
│  ├─ 是 → 用 MCP
│  └─ 否 → 继续
└─ 需要增强工具本身？
   └─ 是 → 用 Plugins
```

**建议：**
1. **先用 Skills**：能用现成的就别自己写
2. **Hooks 用于自动化**：把重复的手动操作配成 hook
3. **MCP 按需添加**：只添加真正需要的外部集成，别贪多
4. **Plugins 看需求**：除非有明确的工具增强需求，否则不用急着装

**复杂任务的正确打开方式：**
- Plan 模式：复杂任务先规划再执行，避免返工

**项目知识的持久化：**
- CLAUDE.md：团队共享的项目知识库，让每次对话都有完整上下文

**扩展生态：**
- Skills 解决标准任务，Hooks 实现自动化，MCP 连接外部世界，Plugins 增强工具
